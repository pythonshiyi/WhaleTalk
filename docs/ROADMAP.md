## 0. 结论先行

### 0.1 现在该升什么

| 事实 | 数据 | 含义 |
|---|---|---|
| 工具数量 | 169 个（11 组、14 个域模块） | 广度足够，第 170 个核心工具的边际价值很低 |
| 最大函数 | `DeepSeekClient.chat` 946 行 | 核心链路把参数、流式、工具、循环、指标、持久化揉在一起，难测试、难回滚 |
| 最大文件 | `api_server.py` 11,600 行 / 122 个 `/v1` 路由 | 路由、业务、SSE、文件、备份、大脑全在一个 `_Handler` 里 |
| 前端热点 | `ChatPage.jsx` 2,459 行 | 界面改动风险集中，缺少组件级与端到端测试 |
| 测试 | 142 个文件 / 1,332 个测试函数（文档口径 1,385 用例），无覆盖率统计 | 测的是「代码不坏」，不是「任务做成」 |
| 智能体评测 | 只有 `tools/memory_bench.py` | 无法回答「v3.29 比 v3.28 强多少」 |
| 依赖 | 33 项，全部 `>=`，CI 只跑 3.12 | 用户机器可能自动装到不兼容的 openai 大版本（开发机实测已到 3.42） |
| 存储 | 会话/索引是 JSON；SQLite 只用于用户数据库 | 无事务、无 FTS，长任务恢复与全局搜索都受限 |
| 平台 | Windows 专用（DPAPI / pywin32 / pyautogui） | 跨平台成本高，短期不应作为主战场 |
| 模型 | 单一 `deepseek-flash` + 备用网关 | 供应商与网络单点，离线不可用 |

### 0.2 三个结构性风险

1. **核心链路耦合**：`chat` 一个函数承担 8 类职责，任何智能体行为改动都要动这里；现有测试覆盖不到 SSE 事件序列与工具编排细节，回归主要靠人肉。
2. **应用层耦合**：`api_server.py` 11,639 行、376 处宽异常捕获；路由增删与业务改动互相牵连，错误语义靠字符串约定。
3. **运行时单点**：依赖不锁版本、只测一个 Python 版本、只支持 Windows、只接一家模型。任何一项变化都可能让「用户那边能跑、这边不能跑」。

### 0.3 三个增长瓶颈

1. **长任务成功率不可测**：能调用 169 个工具，不等于能连续 10 步把一件事做完；当前没有黄金任务集，也没有「一次通过率」口径。
2. **记忆质量没有闭环**：记忆写入有门面与血缘，但检索仍以 IDF 词频为主，没有语义召回、遗忘曲线与冲突消解的量化验证。
3. **扩展成本高**：新增能力只有「改核心表」一条顺手的路；能力包缺少签名、依赖声明与沙箱，生态起不来。

### 0.4 战略主轴

> **先可测，再解耦，再提智，最后扩边界。**

顺序不能反：

- 没有度量，提智是玄学；
- 没有解耦，提智会被回归吃掉；
- 没有稳定的存储与恢复，长任务只是演示；
- 没有评测门禁，模型/生态扩展会把「能跑」变成「看运气」。

## 1. 北极星与护栏指标

### 1.1 北极星

**长任务成功率（LTSR, Long-horizon Task Success Rate）**：在 50 个黄金任务上，一次运行内完成全部验收条件、无需人工修复的比例。任务定义要求至少 3 次工具调用或 2 个回合。

### 1.2 指标表

| 指标 | 定义 | 现状 | 12 个月目标 |
|---|---|---|---|
| LTSR | 黄金任务一次通过率 | 首轮测量 | ≥ 85% |
| 一次通过率 | 无需重跑/人工修复 | 首轮测量 | +15pt |
| 工具失败恢复率 | 工具失败后同任务内换路成功 | 首轮测量 | ≥ 70% |
| 单任务成本 | 元 / 成功任务 | 首轮测量 | -20% |
| p95 首字延迟 | 用户发出到首个 token | 首轮测量 | ≤ 3s |
| 非正常结束率 | error / stopped 作业占比 | 首轮测量 | ≤ 1% |
| 记忆 recall@5 | 100 条记忆查询 | 首轮测量 | ≥ 80% |
| 能力包安装/回滚成功率 | 含签名校验 | 首轮测量 | ≥ 99% |
| 变更风险 | 最大函数行数 / 最大文件行数 | 946 / 11,639 | ≤ 300 / ≤ 3,000 |

### 1.3 护栏

任何优化不得让以下指标明显恶化：

- 单任务成本上升超过 20%；
- p95 首字延迟上升超过 30%；
- 安装包体积上升超过 30%；
- 默认权限模型收紧（能力一条不能少，只允许更可见、更可回滚）。

## 4. P1 / v3.30-v3.31：解耦（7 周）

### 4.1 为什么

`chat` 946 行、`api_server` 11,639 行，是「改一处、炸三处」的根源。先把核心链路拆成可单测的阶段，再谈智能体行为升级。

### 4.2 交付物

1. **`chat/` 包：把 `DeepSeekClient.chat` 拆成 6 个阶段**
   - `chat/prompt.py`：消息布局、缓存友好前缀、图片内联、trailing 上下文；
   - `chat/stream.py`：流式增量、重试、断线判定、usage 归集；
   - `chat/tools.py`：schema 注入、smart_tools 激活、并行执行、参数对齐；
   - `chat/loop.py`：轮次、循环守卫、计划/审批、停止语义；
   - `chat/metrics.py`：TTFT、tps、token、成本；
   - `chat/persist.py`：本轮切片、断连兜底、会话回写。
   - `DeepSeekClient.chat` 只保留编排（目标 ≤ 200 行），对外签名不变。

2. **特征化测试（Refactor 的安全网）**
   - 录制 12 个场景的 SSE 事件序列：纯文本、单工具、并行多工具、smart_tools 激活、停止、断线重试、计划拒绝、审批拒绝、图片输入、JSON 输出、空回复重试、循环守卫；
   - 用假模型回放，断言事件顺序、工具参数、最终消息、usage 一致；
   - 拆分前后逐字节对比，任何差异必须解释。

3. **Runtime 对象**
   - `runtime.py`：`Runtime(data_dir, config, paths, locks, clock, client_factory)`；
   - 工具通过 `runtime()` 取依赖，移除对 `deepseek_client` 可变全局的运行时读取；
   - 验收：单独 `import agent_tools.tool_files` 不触发重复注册；测试可并行、无导入顺序陷阱。

4. **`api/` 包：按域拆路由**
   - `api/chat.py`、`api/sessions.py`、`api/tools.py`、`api/brain.py`、`api/life.py`、`api/files.py`、`api/settings.py`、`api/admin.py`；
   - `api_server.py` 只保留 HTTP 服务器、鉴权、CORS、路由表装配；
   - `_match_routes` 仍是唯一路由表；`test_api_routes.py` 快照 method/path/auth/响应结构。

5. **存储 v2：SQLite**
   - 表：`sessions`、`messages`、`jobs`、`job_events`、`kv`、`schema_migrations`；
   - `messages_fts`（FTS5）支撑全局搜索与会话内搜索；
   - 迁移工具 `tools/migrate_storage.py --check|--apply|--rollback`；
   - 双写一个版本：JSON 与 SQLite 同时写，读走 SQLite，shadow 比对差异；
   - JSON 导入/导出保留，作为可携带备份。

6. **错误契约**
   - 内部统一 `ToolResult(ok, code, message, retryable, data)`；
   - 在工具边界渲染为既有「错误：...」字符串，保持兼容；
   - 逐步把 376 处宽异常按「可重试/不可重试/环境缺失/权限」分类，新增异常必须带分类。

### 4.3 验收

- 最大函数 ≤ 300 行，`api_server.py` ≤ 1,500 行；
- 12 个特征化场景全绿，SSE 事件序列零差异；
- 1 万会话迁移 < 60s，回滚 < 60s，数据零丢失；
- FTS 搜索 p95 < 100ms；
- 现有测试全绿（1,332 个测试函数），四道门禁不降级。

### 4.4 风险

- **拆分引入行为漂移**：先写特征化测试，再动代码；每拆一个阶段单独提交。
- **存储迁移丢数据**：双写 + shadow read + 自动备份 + 回滚命令。
- **API 拆分破坏第三方集成**：路径、方法、响应结构不变；只改内部组织。

## 5. P2 / v3.32-v3.34：提智（14 周）

### 5.1 为什么

工具已经够多，缺的是「把多步任务做成」的稳定性。这一阶段的所有改动都必须先在 P0 的黄金集上证明基线，再上线。

### 5.2 交付物

1. **任务契约（Task Contract）**
   - 每个长任务生成 `goal / constraints / acceptance / budget / deadline`；
   - 契约写入会话，可在 UI 查看与修改；
   - 完成后逐条验收，未通过不得宣称完成。

2. **规划-执行-验证**
   - Planner 产出步骤（每步含工具提示与预期结果）；
   - Executor 执行，Verifier 在每步后检查（文件存在、内容匹配、渲染自检、测试通过）；
   - 失败时有限重规划（≤ 2 次），超过则带着证据向用户求助；
   - 与现有 `task_checkpoint_save/load` 打通，支持中断续跑。

3. **记忆 v2**
   - 混合检索：BM25/IDF + 本地语义向量（ONNX 小模型，约 100MB，可选安装）；
   - 打分：语义 0.5 + 词法 0.3 + 时效/置信 0.2；
   - 遗忘曲线：低价值记忆归档而非删除，用户可见、可恢复；
   - 冲突消解：同 key 取代 + 相似冲突提示；向量只用于提示，不用于自动作废；
   - 记忆评测：100 条查询，测 recall@5、precision@5、过期率。

4. **失败修复闭环**
   - 失败分类：参数/ schema、权限、网络、缺依赖、环境、思路错误；
   - 每类映射修复动作；仅可重试类自动重试，其余升级给用户；
   - 记录「失败→成功」配对，反哺成功模式与技能结晶。

5. **技能结晶 v2**
   - 从「提示词草稿」升级为可执行技能包：参数 schema、步骤、前置条件、测试用例、版本；
   - 技能库 UI：查看、试跑、禁用、回滚；
   - 只有通过测试的技能才允许进入自动复用。

6. **上下文与成本工程**
   - 缓存友好布局已具备，继续做工具 schema 压缩、动态 few-shot、按任务裁剪能力地图；
   - 目标：单任务成本 -15%，不牺牲成功率。

7. **多智能体加固**
   - `team_run` 增加每角色预算、超时、死锁检测、黑板持久化、结果仲裁；
   - 轨迹可视化：谁在什么时候做了什么、花了多少。

### 5.3 验收

- LTSR 相对 P0 基线 +10pt；
- 10 步以上长任务完成率 ≥ 60%；
- 记忆 recall@5 +20%，过期率下降；
- 可重试失败中 ≥ 50% 无需用户介入即恢复；
- 单任务成本 -15%（12 个月累计 -20%），p95 首字延迟不退化。

### 5.4 风险

- **规划器过度设计**：先做「显式步骤 + 验收」，不做自由形式的多智能体社会模拟。
- **向量模型体积/速度**：默认不装，装了就测；不达标自动回退词法。
- **技能自动复用放大错误**：技能必须带测试与版本，失败自动降级为手工路径。

### 12.2 SQLite 迁移草案

```sql
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  name TEXT,
  created_at TEXT,
  updated_at TEXT,
  model TEXT,
  scenario TEXT,
  persona_id TEXT,
  pinned INTEGER DEFAULT 0,
  meta_json TEXT
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL,
  role TEXT NOT NULL,
  content TEXT,
  payload_json TEXT,
  created_at TEXT
);

CREATE VIRTUAL TABLE messages_fts USING fts5(
  content, session_id UNINDEXED, seq UNINDEXED
);

CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  status TEXT,
  created_at TEXT,
  finished_at TEXT,
  record_json TEXT
);
```
