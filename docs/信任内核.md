# 信任内核（Trust Kernel）

> 让智能体的自我修改**可声明 · 可见 · 可回滚**，而不是被禁止。
> 对应模块：`trust_kernel.py` · 账号本：`trust/` · 测试：`tests/test_trust_kernel.py`

## 1. 它要解决什么

决定「智能体能做什么」的代码——`permissions.py`、`security.py`、`crypto.py`、
`snapshot.py`——在默认自由权限模型下，和别的文件没有任何区别：智能体可以读写
任意路径，包括这些文件本身。

后果不是「AI 会不会变坏」，而是一个架构问题：**刹车片放在了油门旁边**。
任何一次提示注入、一次模型幻觉、一次「顺手把限制去掉好完成任务」的善意自作
主张，都会永久改变权限模型——而且改完之后程序照常启动、照常以全权限运行，
**没有任何人知道发生过什么**。

三个具体缺口（改造前实测）：

| 缺口 | 证据 |
|---|---|
| 护栏可被无痕改写 | `write_file` 只过 `check_filesystem`；blacklist 模式 `blocked_dirs` 默认 `[]` → 全部放行 |
| 唯一有验证的通道是关的 | `self_evolve` 要求项目含独立 `.git`；无 `.git` 时直接报错，而直接写文件的路畅通 |
| 能力开关关不掉 | `SELF_EVOLUTION_TOOLS` 注释明写「不受 `enabled_tools` / `tools_enabled` 控制」 |

## 2. 设计立场：不夺权

修法有三条路，我们**刻意选了第三条**：

1. 禁止智能体写这些文件 —— 夺权，与「默认自由 + 用户掌权」的产品立场冲突；
2. 在 `write_file` / `edit_file` 里设卡 —— 假安全。`run_python`、`run_command`、
   `start_process` 都能直接写文件，工具层设卡只挡君子；
3. **不设卡，改「效果」** —— 智能体依然可以改任何东西，但从现在起，对内核的
   改动会被登记、留档、如实报告，并且永远可以一键回滚。

我们相信这才是「伙伴而非工具」的做法：**不铐住对方，而是让对方无法对自己隐瞒
自己做过什么，也让用户永远握有知情权与撤销权。**

## 3. 强制点为什么在「效果层」

既然工具层挡不住，可靠的核对点就只有两个：

- **启动时**：`api_server.start_server` 调用 `trust_kernel.boot_check()`，把当前
  文件与可信基线逐字节比对，未被声明的改动生成 incident 事件；
- **对话时**：存在未确认改动时，`_inject_system_messages` 注入「自我完整性」提示
  ——把「不可隐瞒」变成对话里的可见事实。干净时返回空串，**零 token、不扰动
  前缀缓存**。

另外提供 `GET /v1/trust`（`?deep=1` 现场重算）与 `/v1/status` 的 `trust` 摘要，
让前端与外部工具都能读到状态。

### 三个通道的关系

```
声明通道   write_file / edit_file ──declare──commit──▶ 基线推进 + 账本（正常流水）
旁路通道   run_python / 外部编辑器 / 其他进程 ────────▶ 启动核对发现 ──▶ 事件 + 提示
用户通道   CLI accept / restore ──────────────────────▶ 确认保留 或 回滚
```

## 4. 事实来源：基线优先，索引兜底

`trust/baseline/<name>` 保存可信副本，`trust/manifest.json` 只是索引。

**删掉 manifest 并不能让改动「看不见」**：核对时优先逐字节比对基线副本，基线
缺失才退回指纹。而且 manifest 丢失本身就是一个事件——如果账本存在却找不到
`manifest.json`，会记 `manifest_lost` 事件后在 manifest 里标 `bootstrapped_as`，
绝不「重建成看起来一切正常」。

> 踩坑记录：`bootstrapped_as` 最初写成持久字段 `mode`，而读取方拿它当「刚刚发生
> 过重引导」的信号 → 告警在**每次启动**重复触发。现改为模块级 `_last_bootstrap`，
> manifest 里只留历史记录。回归用例：`test_manifest_lost_alert_fires_once`。

## 5. 两种模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `report`（默认） | 只报告、只留痕、**不修改任何文件** | 开发期：用 IDE 改内核文件是正常行为，程序不该擅自回滚用户的编辑 |
| `guard` | 把改动隔离到 `trust/quarantine/<ts>/` 并从基线恢复（原件保留） | 部署实例：改动需先声明才生效 |

配置：`trust/config.json` 的 `mode` 字段，或 CLI 用 `tk.init(mode="guard")`。

**为什么默认 `report`**：本仓库处于活跃迭代中，默认 `guard` 会与开发者的正常
编辑流程对撞（每次改完都被回滚），反而逼人关掉整个机制。`report` 用"不再沉默"
换取了可持续性；需要硬保证的场景一行配置即可切到 `guard`。

## 6. 目录语义（刻意分开，避免异常被淹没）

| 路径 | 内容 |
|---|---|
| `trust/baseline/` | 可信基线副本（不参与快照 200 条轮转，永不被裁剪） |
| `trust/manifest.json` | 基线索引（sha256 / size / mtime / 登记时间 / 方式） |
| `trust/ledger.jsonl` | 声明式账本，append-only，一行一次改动 |
| `trust/history/` | **已声明**改动的历史副本（声明前 / 回滚前），用于撤销一次合法改动 |
| `trust/incidents/` | **未声明**改动的事件与证据副本 |
| `trust/quarantine/` | `guard` 模式隔离出来的原件 |
| `trust/STATUS.md` | 人类可读状态，可直接打开 |

## 7. CLI

```bash
python trust_kernel.py status            # 看状态（--deep 现场重算）
python trust_kernel.py verify            # 立即核对（rc=2 表示有未声明改动）
python trust_kernel.py diff permissions.py     # 先看改了什么
python trust_kernel.py restore permissions.py  # 回滚到可信基线
python trust_kernel.py accept --all      # 确认保留并推进基线
python trust_kernel.py log -n 20         # 看账本
```

## 8. 明确不做的三件事（非目标）

1. **不阻止写入、不阻止执行**：能力一条不减，权限模型与 `full_auto` 语义不变。
   写 `trust_kernel.py`、改 `permissions.py`、`accept` 自己的改动——都仍然做得
   到；区别只在于**都会留下痕迹**。
2. **不代替用户做决定**：默认只报告，不擅自回滚；处置权在用户。
3. **不假装防得住有持久意图的攻击者**：密钥可读、账本可写，模块提供的是
   「可检测、可追溯、可撤销」，**不是「不可伪造」**。真正的防线是让每一次自我
   修改都留下痕迹并出现在用户眼前。

第 3 条是有意的取舍：要做成不可伪造，就得引入只有智能体碰不到的密钥与校验
路径（例如把校验移出它可读写的范围），那需要改变进程模型与部署形态，超出
本次范围。当前设计在"不夺权"约束下做到了可得的最强形态。

## 9. 内核清单的取舍

只纳入**授权判定**类文件：

```python
PROTECTED = ("permissions.py", "security.py", "crypto.py", "snapshot.py", "trust_kernel.py")
```

刻意**不**纳入 `agent_tools/tool_*.py`、`deepseek_client.py`、`api_server.py`——
这些是业务实现，会被正常迭代；纳入只会制造噪音，反而让真正的异常被淹没。

用户可通过 `trust/config.json` 的 `extra_protected` **追加**，但无法用它**摘掉**
（`protected_names()` 只做并集），所以配置文件本身不能成为削弱保护的途径。

## 10. 已知边界

- **工具层只覆盖 `write_file` / `edit_file`**：经 `run_python`、外部编辑器、其他
  进程的改动一律走"启动核对发现"的路径（按设计，见第 3 节）。`delete_file` 删除
  内核文件会被识别为 `missing` 并报告。
- **核对发生在启动期**：运行期被改写、且进程未重启时，`/v1/trust?deep=1` 可现场
  发现，但不会自动介入（不夺权）。
- **首次运行是「首次使用即信任」（TOFU）**：`trust/` 已被 `.gitignore` 忽略，新克隆
  在第一次启动时以**当时的代码**为可信基线。因此如果代码在首次运行*之前*就被改过，
  基线会把改动当成正常的——这是所有无外置锚点的完整性方案的共同起点。要摆脱它，
  需要把基线放在智能体读写范围之外（例如随发布包签名分发），见第 8 节第 3 条。
- **与 git 行尾归一化的交互（已处理）**：本仓库是 git 工作区且常开 `core.autocrlf=true`，
  一次 `git checkout` / `pull` / `stash` 就会把工作区文件整体改写成另一种行尾——字节
  全变、语义一字未改。`verify()` 会把这类差异标注为 `cosmetic`（`cosmetic_only` 汇总），
  报告与注入文案会说明"差异仅限行尾，多为 git 检出所致"。
  **标注不等于放行**：仍然记事件、仍然算未确认，只是把结论说清楚，避免噪音淹没真异常。
  确认无碍后 `accept --all` 即可。
- **快照与信任内核是两套机制**：`snapshot.py` 管"任何写操作的前后备份，200 条
  轮转"；信任内核管"内核文件的基线，永不裁剪"。两者互不覆盖。
- 直接 `import agent_tools.tool_files`（绕过 `deepseek_client`）会触发工具名重复
  注册——这是既有的导入顺序契约，与信任内核无关。
