# P0 架构收口：上下文装配 · 退化日志 · 工具钩子管线

> 对应提交：`feat(arch): P0 架构收口`（v3.10.0 未发版追加）
> 模块：`context_providers.py` · `degrade.py` · `tool_hooks.py`（+ `toolkit.py` 包装点）

## 0. 这一批要解决的是同一类问题

不是"哪里写得丑"，而是**横切关注点没有被收口**。取证（改造前）：

| 现象 | 数字 |
|---|---|
| 静默吞噬异常 | `except …: pass` **326 处**（api_server 97 / tool_docs 50 / deepseek_client 35） |
| 上下文装配 | `_inject_system_messages` 单方法 **128 行**，串 9 个来源，全在 `try/except: pass` 里 |
| 横切逻辑分布 | `tool_trace`/`request_approval` 已集中；`snapshot_before` 散在 2 文件 4 处；`clamp_int` 散在 6 模块 17 处；信任声明只能逐工具手接 |

共同后果：**每加一个横切保障，都要改 N 个文件**；出了问题**没有信号**。

## 1. P0-3 退化日志（`degrade.py`）

```python
try:
    ...
except Exception as e:
    degrade("context.memory", e, "长期记忆未注入，本轮可能答不出偏好", critical=True)
```

- 按 key 归并计数（同类反复失败只累加，不刷屏）；节流日志；原子落盘 `DATA_DIR/degradations.json`。
- **critical 分级**：只有影响回答质量的降级才进注入文本。326 处无害降级不该占 token，
  也不该让模型以为自己随时在坏掉。
- `critical_notice()` 是**自我状态**而非错误日志：让 AI 知道自己的状况，
  并**如实告知用户**，而不是在能力受损时继续自信作答——与信任内核同一立场。
- **永不抛出**：记录自身出问题也不得反噬主流程（有测试锁定）。

## 2. P0-2 上下文装配 Provider 化（`context_providers.py`）

9 个来源变成 `Provider(name, priority, budget, critical, enabled, provide)`，装配器统一：

- **排序**（顺序变了 = 前缀缓存失效 + 行为漂移，有测试锁死）；
- **预算**（`budget` 超限截断并标记 `truncated`；安全上限，正常不触发）；
- **回执**：`injected[{name,chars,truncated}] / skipped[{name,reason}] / failed[{name,error}]`
  —— "这一轮注入了什么、为什么贵、谁坏了"首次变得可回答；
- **失败不再静默**：逐个 try/except + `degrade`（带影响说明）。

**行为等价是硬约束**：注入内容与顺序与改造前完全一致（仅新增 `context.degrade_status`，
无关键降级时返回空、不占位）。`tests/test_quiet_mode.py` 原样通过。

回执经 `last_receipt()` 由 **既有** `GET /v1/context` 暴露（不新增路由，避免端点数漂移）。

> 设计细节：依赖（`_memory_full` / `dc.self_profile` / `brain_api` …）以 **thunk** 形式注入，
> 在调用时按名字解析模块属性。原因有二：① 既有测试用「桩 module 属性」验证注入，
> 提前缓存函数对象会让桩失效；② `import brain_api` 的失败被隔离在该 Provider 内。

## 3. P0-1 工具钩子管线（`tool_hooks.py`）

### 为什么包装在「注册处」而不是「分发处」

`execute_tool` 只是众多调用路径之一——`/v1/tools/<x>/invoke`、工作流、子智能体、
测试直调都绕得过去。而 `@tool()` 是**唯一的声明确认点**（toolkit 六层全部由它生成）。
在这里包装意味着：**任何调用路径都逃不掉钩子，新增横切保障只需注册一个钩子。**

### 已有能力

| 钩子 | 范围 | 作用 |
|---|---|---|
| `trust_declare` / `trust_commit` | 全局 | 路径参数命中信任内核文件时自动声明（结果还会追加一句"已登记"给模型看——透明性对所有 148 工具通用，不必逐个手写） |
| `snapshot` | 声明式 | `@tool(hooks=("snapshot",))`；快照一个工具只需一行声明 |

### 硬约束

- **绝不改变工具语义**：钩子抛错一律吞掉 + `degrade` 留痕；工具自身异常**原样上抛**
  （分发层仍按原逻辑格式化为"工具执行失败: …"）。
- `functools.wraps` 保证 `__name__` / `__doc__` / `inspect.signature` 对调用方不变。
- **post 必须在 `return` 之前跑完**：写在 `finally` 里的话，`return` 表达式会先求值，
  post 对结果的补充（信任声明回执）就落不到返回值上。

## 4. 过程中被测试抓出的自身缺陷

1. **死锁（首次工具调用即挂住）**：`_ensure_builtins()` 持锁期间调用 `hook()`，而 `hook()`
   也要持同一把非重入锁 → 必须用 `RLock`。
2. **快照钩子漏判 `ctx.declared`**：会对**所有**带 `path` 参数的工具无差别快照，
   而不只是声明的那些。
3. **`brain_api` thunk 用法不一致**：漏了调用，拿到的不是模块对象而是函数 →
   `tests/test_quiet_mode.py` 立刻失败（同时 degrade 精确报出原因，这正是新机制的价值）。
4. **控制流错误**：`return` 在 `finally` 之前求值，post 钩子改不动返回值。
5. 行尾：`api_server.py` 实为 LF，替换脚本误插了 75 行 CR → 已统一。

## 5. 明确不做（守住"不夺权"）

- **不阻断任何工具**：钩子只做登记、留痕、快照，不做闸门。
- **不合并既有端点、不给 `write_file`/`run_python` 加拦截、不合并 `snapshot` 与 `trust_kernel`**。
- **`clamp_int` 参数钳制暂不迁移**：它是 17 处行为敏感点，迁移需逐个核对钳制区间，
  留作 P0-1 第二步（见 MODULES.md「演进建议」）。
