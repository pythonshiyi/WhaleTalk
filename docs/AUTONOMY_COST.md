# 自主运行的成本与内存预算

决定一件事：**定时自主用什么实现**。答案是操作系统的计划任务，不是 LLM 定时器。

## 为什么不用 LLM 定时器

`schedule_task`（agent 内定时）到点会唤醒一次 LLM 推理，每次都是：

- 一次完整上下文组装（system prompt + 记忆 + 工具表，实测 prompt 缓存命中 99.4% 时仍计费）
- 一个常驻会话的内存峰值

用 LLM 定时做「每天备份一次」是拿推理能力干 cron 的活。换 Windows 计划任务，同样的效果，
**LLM 成本为 0，常驻内存为 0**（脚本跑完即退）。

## 现在跑的是什么

| 任务 | 频率 | 做什么 | 峰值内存 | 时长 | LLM 成本 |
|---|---|---|---|---|---|
| `WhaleTalk_BrainArchive` | 每日 03:30 | `brainkit.py archive`（快照 + 镜像到 `manifest.archive_mirror`） | ~40 MB | ~2 s | 0 |
| `WhaleTalk_ProjectBackup` | 每周日 04:00 | `backup.py --prune 8` | ~35 MB | ~5 s | 0 |

脚本在 `tools/scheduled/*.bat`，日志在 `data/logs/{brain_archive,project_backup}.log`。
两条都不常驻、不轮询、不留后台进程；任务计划本身就是 OS 的最小调度单元，开销可忽略。

**内存纪律**：任何自主行为都必须是「起进程 → 干活 → 退出」的短生命周期形态。
做一个常驻守护进程轮询状态，会白白吃掉几十 MB 内存换一个 cron 就能做的事。

## 三档成本模型

1. **零 LLM（首选）**：确定性脚本能做的，全部交给 OS 计划任务。
   归档、备份、清理、校验都属于这一档。
2. **按需 LLM（默认交互）**：用户发起才推理。
3. **受控 LLM（仅当需要判断时）**：真的有「要读懂情况再决定」的需求才开，
   且必须带预算门限（每次唤醒的 token 上限 + 每日次数上限），否则宁可不做。

## 不做的事

- 不做每分钟/每五分钟的轮询心跳（除了烧钱没有任何信息增益）
- 不做常驻 watcher 进程（内存换不到确定性收益）
- 不在用户活跃时段跑批量任务（避开 9-12 / 14-18 高峰）

## 备份体积实测

排除浏览器纯缓存与历史工作产物后：

- 修复前：179 MB / 1943 文件
- 修复后：8.8 MB / 953 文件（保留 Cookies、Login Data、Local Storage，登录态不丢）

`--prune 8` 时 8 份合计约 70 MB，不再是需要担心的量级。
